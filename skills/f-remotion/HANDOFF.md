# f-remotion 交接状态

> 更新时间：2026-09-14。此文件用于新的 Codex 对话接续维护和迭代，不属于普通视频任务的运行时风格规范。执行视频任务时仍以 `SKILL.md` 及其直接引用资源为准。

## 新对话接手方式

1. 完整读取 `SKILL.md`，再按其中路由读取必需资源。
2. 读取本文件了解已确认的设计决策、失败方向和最近验证状态。
3. 把透明合成、中文可读性、事实来源、人物安全、逐帧确定性和叙事分组当作稳定基线；每片调色、构图、材质和运动由新导演人格重新定义。
4. 新方案先在真实视频中验证；只有用户明确确认后，才写回 Skill 的稳定规则或资产。
5. 每次形成新的确认结论，同步更新 `SKILL.md`、对应 reference 与本文件。

新对话可直接说：`读取 f-remotion 的 SKILL.md 和 HANDOFF.md，从当前版本继续优化，不要重新设计。`

## Skill 目标

把目标视频和 SRT/时间轴制作成有独立视觉方向、按帧可执行的 Remotion 画中动效。核心能力是先做语义编辑，再由画面动效导演建立本片专属的调色、构图、材质、编舞和退场，最后由实现层忠实落地。

## 已确认的稳定基线

- 名称保持 `f-remotion`。
- 默认调用语保持简短：`使用 $f-remotion。`
- 无需再次提供参考视频；旧 V4 样板只在导演计划完成后校准可读性、密度和完成度。
- 稳定基线是中文可读性、透明根画布、事实与素材来源、动态安全区、逐帧确定性、叙事分组和足够留白，不再固定深色卡片、蓝绿红黄、左侧堆叠或柔和淡入上移。
- 每条片必须运行内部 `director/SKILL.md`，在不读取旧场景库的状态下发散三个结构不同的方向，并生成可校验的 `analysis/motion-plan.json`。
- 现有原型、V4 源码和 `SemanticMotionPrimitives.tsx` 只在计划通过后作为工程零件；不匹配时直接新写组件。
- 一个大视觉组对应一个完整叙事任务，不按字幕条数、句数或固定秒数切换；同一主锚点可以跨多句驻留。
- 一次只显示一个大视觉组；上一组完全退出后下一组才进入，组间可以有意留白。
- 元素跟随口播关键词逐步进入。新属性、证据、层级或转折出现时局部更新；继续解释同一信息时允许稳定保持。
- 中文承担主要信息。英文只保留原话、官方名称或必要行业缩写。
- 不使用扫描线、常驻进度条、技术网格、假数据、随机字符和无来源微文案。
- 动效保护人物、手势、原字幕、产品和用户已添加素材；布局按逐段动态安全区和本片构图系统决定。
- SRT 默认只用于语义和帧时间轴，不自动生成成片字幕。
- 用户已插入截图、录屏、B-roll、画中画或信息卡的区间是硬禁区；包括场景根背景和退场残影在内的 Remotion 图层都不得进入。
- 国家、地区、平台、组织和产品可在确有识别价值时使用有来源的图标/标志；可靠数据可使用证据图表、数字增长和区间计数，不记忆固定 Logo、不虚构数据。
- 用户确认前不覆盖旧版，不修改 V4 基准资产，输出使用新文件名或独立 Composition。
- 第一版及用户确认前的修改版固定输出 1080p 级 1K/30fps 审片视频；用户确认画面后才按指定分辨率与帧率渲染正式版。
- `motion-plan.json` 固定使用 30fps 审片时间基准；实现先换算为秒，再适配正式 Composition 的 fps，避免升帧率后同步漂移。
- 审片阶段只保留一次计划校验、一次最快代码检查、一次完整草稿渲染和媒体参数探针；逐场证明帧、多边界预览、渲染式 A/B 与全片解码改为风险触发或正式交付动作。

## 已否决或明确不推荐的方向

- 每段固定放一个大英文标题。参考片中的行业缩写属于话题，不是风格模板。
- 为了“科技感”增加横扫线、扫描线、常驻进度条、技术网格或假数据。
- 为证明学会参考片而把其中所有组件强行塞进目标视频。
- 过多小标签、印章、图标和辅助文案。若主信息已经表达清楚，应删除这些小东西。
- 动效一开始快速全部播放完，随后长时间不变化。
- 相邻场景视觉交叠，或在上一组仍存在时让下一组出现。
- 只看参考片稳定帧，不分析入场顺序、阶段变化和退出方式。
- 在导演计划前读取旧资产和原型，再把历史外观包装成“新创意”。
- 让每个大动效携带不同色的全屏暗部渐变或调色层，再随场景一起淡入淡出。
- 按“每两句一个动效”、每条字幕或固定秒数机械切换大动效。

## 已沉淀的能力

- 语义匹配：重点、定义、顺序、因果、对比、并列、层级、边界、状态变化与数据。
- 必要性判断：人物表演或已有素材已经足够时主动留白。
- 原型能力：中文钩子、条件分支、决策路径、步骤状态链、核心揭晓、定义/实例、边界清单、结论确认卡。
- 可选构造能力：整词级联、状态替换、阶段轨道、视觉锚点驻留、实体标识行、确认动作、真实数字增长、区间计数、证据比较图、数据条、累积堆叠、门槛/解锁和概念组装。
- 创造流程：先隔离旧库，发散至少三个在主轮廓、阅读路径和运动法则上不同的方向，再与无动效基线比较。
- 导演计划：保留三个 directionExploration 与 selectedDirection，并记录 thesis、governingMetaphor、palette、typography、compositionSystem、surfaceSystem、motionGrammar、逐场 choreography、exitLogic、proofFrames 和无动效对照。
- 可行性分级：`native / dependency / preproduction`；高风险方案需要确认依赖/资产并提供等义回退。
- 参考片学习：拆分为制作底线、导演可选机制、不可照抄话题内容和素材/镜头依赖；参考片不能跳过原创方向比较。

## 最近一次真实项目验证

最近使用一条约 12.6 秒、4K、59.94fps 的口播短片进行了完整验证。用户要求不显示字幕，并要求已经插入网页画面的区间不添加动效。

处理结果：

- SRT 仅用于语义同步，没有生成字幕层。
- 用户插入画面及其淡入淡出期间被标为硬禁区，完全没有 Remotion 图层。
- 其余口播只选择三个高价值语义点，分别采用数字重点、克制问题卡和分阶段核心揭示。
- 组间保留干净空隙，长组按新增台词逐步更新，避免提前播完后长期静止。
- 已通过 TypeScript/ESLint、关键帧、低清连续边界、4K 正式渲染和全片解码检查。

本次实战将“字幕默认不渲染”和“已有画面硬禁区”提升为稳定规则，已经写入 `SKILL.md`、`references/implementation.md` 与 `references/validation.md`。

## 2026-09-11 透明画布与叙事组迭代

用户复看上述成片后指出：三个大动效各自携带不同色的全屏渐变/调色层，且场景整体淡入淡出，导致原视频左侧背景随切组快速闪暗、闪亮和变色。根因已在 `DoubaoBusinessMotion.tsx` 的 `SceneCanvas` 中确认，不是单纯的退场帧数问题。

对 `参考视频1.mp4` 逐帧复核时，忽略了博主自己的截图、网页和视频画中画，只统计图形动效：

- 约 4.0–15.75 秒是同一个概念锚点。`FDE` 建立后跨多句驻留，未来周期、持续增长、不可替代和建议只做局部补充，没有按两句换景。
- 约 16.0 秒存在主动留白；17–19 秒附近的数据条只在“讨论热度/证据”语义成立时生长，基准、对照值和增幅按顺序完成。
- 约 20.5–25.25 秒把英文全称和中文拆解视为同一个定义任务，逐词/逐层组装后整体退出。
- 约 27.0–31.75 秒把国外、互联网大厂和二线城市/孵化园区放在同一个需求分层组中，国家与平台标志按层级逐行补入。
- 约 33.2–34.6 秒的数字表现先建立量级语境，再让区间上界增长到目标值，完成后稳定驻留；不是随机滚数。

本轮确认并写回：场景根画布默认透明；历史全屏暗部渐变/语义调色废弃；大动效按完整叙事任务而非句数分组；`enter/update/hold/exit/blank` 成为组内节奏事件；实体标识行、证据比较图和区间计数进入“可选”能力。局部深色卡片仍可保留，但不是动效背景。

## 2026-09-14 画面动效导演迭代

用户指出旧流程虽然语义判断正确，但每条片会重复蓝绿红黄、暗色卡片和相近进退场，根因是创意前置加载了 V4 样板、场景原型和动效库，导致模型从库存组件倒推画面。

本轮把流程改成“语义编辑 → 画面动效导演 → Remotion 实现”三层：

- 新增内部 `director/SKILL.md`。它先读完整视频与 SRT，在不查看旧库的状态下提炼画面母题，并强制发散至少三个在轮廓、阅读路径和运动法则上不同的方向。
- 每条片重新定义 palette、typography、compositionSystem、surfaceSystem、motionGrammar、continuityDevice 与 blankStrategy；旧 V4 颜色、暗卡和淡入上移不再是默认值。
- 每个视觉组必须规划稳定态、z-order、严格出场顺序、update/hold、exitLogic、proofFrames、与前段差异及无动效基线。
- 新增 `director/remotion-capability-map.md`，把方案分为 `native / dependency / preproduction`，明确 Remotion 能做什么、何时需要依赖或外部预制资产。
- 新增 `scripts/validate_motion_plan.py`，编码前校验时间范围、禁区、场景交叠、编舞事件、关键帧、依赖和回退。
- `scene-archetypes.md`、`motion-library.md`、V4 源码和通用原语被降级为计划通过后的工程零件，不能参与第一轮创意。

旧 V4 资产仍保留，用于计划完成后的可读性、密度和完成度校准；不得用它重新锁死每片的视觉风格。

## 2026-09-14 快速审片与正式交付迭代

用户指出 F Remotion 的大部分耗时来自首版前的重复检查，而创意尚未确认时直接渲染高分辨率、高帧率正式版也造成浪费。本轮把验证与输出拆成两个明确阶段：

- 首版和所有确认前修改统一使用 1080p 级 1K/30fps；横版 `1920×1080`、竖版 `1080×1920`、方形 `1080×1080`，其他比例保留原纵横比。
- 审片版默认只做一次计划校验、一次最快 lint/typecheck、一次完整渲染和媒体流参数核验。逐场景 `proofFrames`、全部边界短片、渲染式有/无动效对照与全片解码不再是首版必做项。
- 只有长中文溢出、复杂遮罩、人物/字幕遮挡、dependency/preproduction、复杂边界或透明背景异常等具体风险出现时，才补少量静帧或一个代表短片段。
- 用户明确确认当前画面后，才读取指定分辨率与帧率并渲染正式版；全片解码只在正式交付执行一次。
- 为避免 30fps 审片升到 50/60fps 后整体失速，导演计划永久使用 30fps 时间基准，实现层通过“计划帧 ÷ 30 = 秒，再乘运行 fps”转换所有事件与时长。
- 只改变同纵横比分辨率/fps 不重做导演方案；若改变纵横比，先在新比例下再走一版 1K/30fps 审片确认。

## 新会话接手验证

2026-09-10 使用一个未继承旧聊天上下文的独立代理做了只读接手测试。代理仅凭 `SKILL.md`、本文件和原始视频/SRT，准确恢复了 V4 唯一稳定基线、实验版本非基线、已有画面硬禁区、SRT 默认不渲染、留白/语义策略、无交叠时间轴和全部禁用元素。未发现会阻塞下一会话的信息缺口。

2026-09-11 修改后又用未继承本轮诊断结论的独立代理做了 20.5 秒原始口播前向测试。它正确使用透明根画布，把跨句的“持续增长 + 难被替代”合并为同一 `visualGroupId`，对无可靠资产的平台实体降级为文字行，并按顺序处理 `643 → 5330 → +729%` 与 `30K–60K`。未出现按两句换景、虚构 Logo、虚构单位或全屏背景回退。

后续执行时仍需听取真实音频，微调 SRT 句内关键词的精确落点；SRT 只有句级时间时，不得把均匀字符分配当作最终词级同步。

## 资源职责

- `SKILL.md`：三层工作流、创意隔离和不可违反规则。
- `director/SKILL.md`：内部画面动效导演人格与 `motion-plan.json` 交付协议。
- `director/remotion-capability-map.md`：Remotion 能力分级、性能风险与等义回退。
- `references/style-preset.md`：稳定制作底线与每片可导演变量。
- `references/semantic-matching.md`：只做动效必要性、叙事分组和时间语义，不指定外形。
- `references/scene-archetypes.md`：计划确定后可参考的历史工程原型。
- `references/motion-library.md`：计划确定后可复用的构造能力。
- `references/implementation.md`：时间轴、组件与 Remotion 实现约束。
- `references/validation.md`：快速审片、风险触发检查与正式交付验收。
- `references/reference-analysis.md`：只有用户提供新参考片并要求学习时使用。
- `assets/approved-v4-source/` 与 `assets/style-board.svg`：计划完成后的历史完成度参照，不参与第一轮创意。
- `assets/SemanticMotionPrimitives.tsx`：计划完成后按需取用的构造材料，不是视觉答案。
- `scripts/srt_to_timeline.py`：字幕到帧时间轴工具。
- `scripts/validate_motion_plan.py`：导演计划的结构、时间、禁区和可行性校验。

## 后续迭代协议

1. 先在独立 Composition 或新输出文件中试验，不覆盖用户满意版本。
2. 区分“能力不好”和“本片不匹配”；后者不应直接从能力库删除。
3. 用户仅确认某条视频成片，不代表所有新组件自动成为默认模板。
4. 只有跨项目验证且用户明确认可的规则，才提升为稳定基线。
5. 每次提升后更新对应 reference、必要资产、本文件的“最近验证”和“已确认基线”，再运行 Skill 校验。
